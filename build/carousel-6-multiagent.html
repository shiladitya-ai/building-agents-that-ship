The big migration

Four specialists. One incoherent whole.

Planner. Mapper. Validator. Executor. Clean separation — just like microservices.

> mapper changed the schema; planner never saw it
> validator checked assumptions the executor had dropped
> two agents ran the SAME step

We spent more time reconciling the agents with each other than doing the migration.

Why the instinct feels right

It borrows credibility it hasn’t earned.

  • The microservices analogy — we decompose big systems, so decompose big agents.
  • “Specialists are better” — a tight validation agent beats a generalist.
  • The parallelism dream — five agents must be faster than one.

All reasonable. All applied to the wrong layer.

Production-Grade Agentic AI@shilsr · 3 / 8
The real reason

Microservices pass payloads. Agents must pass context.

A schema or API crosses a boundary cleanly. The fuzzy, evolving understanding of what we’re doing and why does not.

Every handoff leaks shared understanding. Each agent acts on a partial view — locally sensible, globally wrong.

The tax you pay

Three costs stack up fast.

  • Compounding errors — across four agents, mistakes don’t add. They multiply.
  • ~15× the tokens — context gets re-sent and re-reasoned at every seam.
  • Debugging collapses — the bug lives in the conversation, not any one agent.
Production-Grade Agentic AI@shilsr · 5 / 8
Not anti-multi-agent

When it wins decisively.

Breadth-first, parallelizable, context-independent work: many subtasks that run at once, don’t depend on each other, share no evolving state.

“Research these 40 companies.”
“Assess 500 tenants against a fixed checklist.”

Fan out → run in parallel → merge. No shared context to fragment.

Production-Grade Agentic AI@shilsr · 6 / 8
The tell

One question decides it.

Do the subtasks need to talk to each other while they run?

NO →

Fan them out. Multi-agent wins.

YES →

A coordination problem in a parallelism costume. One agent wins.

The migration was a loud YES. That’s why it broke.
